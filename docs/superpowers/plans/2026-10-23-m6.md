# M6 Slack: Implementation Plan

> **For agentic workers:** use superpowers:subagent-driven-development and
> superpowers:test-driven-development. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `bosun notify` with the channel check, `bosun answer` with owner Slack IDs, thread
spawn with intake first, and exactly one thread reply per child result (M6, UC-M6-1..4), built
and tested against a fake only.

**Spec:** §10 (Slack stream), D11 (Slack through Claude Tag only), D29 (bosun never calls session
tools; it returns them in `next`), §8 (`bosun ask`, owners), §12 M6. The seed constraints hold:
one task per PR of about 400 lines, `src/core` does no I/O, tests never reach a real API, one
envelope on stdout, `error.fix` never empty.

## Decisions

Each decision has a default that fails closed. S1-S8 are confirmed by the orchestrator
(2026-10-23); **Owner** marks what the owner sets up.

- **S1 No Slack app, no token.** §10 says the Slack stream needs only Claude Tag and
  GitHub. bosun therefore never calls the Slack API and holds no Slack secret. Like D29, a
  command that must post returns the post in `next` as `{"tool": "slack_post", "args":
  {"channel", "thread_ts"?, "text"}}`; the Claude Tag thread or the notify Routine makes the call
  with its own Slack tool and then acknowledges it (S4). The alternative, a Slack app with a bot
  token (`SLACK_BOT_TOKEN`, env only, scopes `chat:write`, `channels:read`, `groups:read`,
  `users:read`), would let bosun check the channel itself; it contradicts §10 and adds a secret,
  so it is not built unless the owner asks for it.
- **S2 Channel check from facts the caller supplies (UC-M6-1).** Without a token bosun cannot read
  the channel, so `bosun notify` takes the channel facts as JSON: `--channel-info -|FILE` with
  `{"id", "is_ext_shared", "is_org_shared", "is_shared", "guests"}` (`guests` is the number of
  members with `is_restricted` or `is_ultra_restricted`), which the caller reads with its Slack
  tool. bosun refuses (exit 5, needs-human, nothing to post) when the id is not `[slack] channel`,
  when any shared flag is true, when `guests > 0`, or when the info is missing or has an unknown
  shape. The check is only as good as the caller's facts; with S1 that is the accepted residual,
  written down in the spec. Owner: the channel must be a private, non-shared channel without
  guests.
- **S3 Owner Slack IDs (UC-M6-2).** `governance/owners.toml` already has an optional `slack =
  "U…"` per owner (R-gov, read from the default branch, as `bosun ask`). Only those IDs count.
  No owner with a `slack` ID means no answer counts and no thread may spawn (fail closed). Owner:
  add `slack = "U…"` to their `[[owner]]` table. `bosun doctor` warns when no owner has a
  `slack` ID while `[slack] channel` is set, so the silent no-op is visible.
- **S4 Exactly once by record (UC-M6-4).** A post is a pending notification until it is
  acknowledged: `bosun notify --ack <key>` writes a `notified` record (`{"bosun":"notified",
  "key", "at"}`) on the registry issue, and `bosun notify` never returns a key that already has
  one. Keys are stable: `ask:<issue>:<comment>`, `main-red:<issue>`, `result:<epic>:<comment>`,
  and so on. A caller that posts but dies before `--ack` causes at most one repeat; one that acks
  without posting loses one post. Both are visible in the registry.
- **S5 Answer.** `bosun answer <issue> --slack-user U… --from -|FILE` (the answer text on stdin):
  if the issue has an open `ask` record and the Slack user is an owner ID (S3), bosun comments an
  `answer` record with the text (fenced, as data) and returns ok. The answer never changes the
  task's state: the owner moves the task out of `needs-human` on GitHub. Any other user gets
  exit 5 and nothing is written.
  The Slack user ID comes from the Claude Tag event, never from the message text.
- **S6 Thread spawn (UC-M6-3).** `bosun spawn --slack-thread <ts> --slack-user U… --request -`:
  the user must be a spawner (`[slack] spawners = "owners"`: an owner Slack ID; nothing else is
  accepted in M6) and `[slack] may_spawn` true, else exit 5. If no issue is ready, bosun runs
  intake with `--source slack` (the request as data), which opens a kind/plan task, and spawns on
  that task with the same 7 checks as any spawn. The thread ts is stored in the child's lease and
  the spawn record, so the result can find its thread. `may_build = false` stays: the thread never
  writes code, only the spawned child does.
- **S7 Thread reply (UC-M6-4).** A `result` record on an epic whose spawn carries a thread ts is a
  pending `thread-result` notification (S4) with `thread_ts` set. The live thread session lists it
  with `bosun notify --thread TS`, posts it and acks; if the thread ended, the notify Routine
  (no `--thread`) finds it still unacked after a 15 minute grace period and posts it into the
  thread. Either way the ack makes it exactly one reply.
- **S8 Slack text is data.** Request and answer text is fenced and neutralised like intake text;
  it never becomes a bosun flag or a label, and Slack never approves risk (no path from Slack to
  `risk-check`).

## Residual risk and a later option

- **Channel facts are the caller's.** With S1 bosun cannot read Slack, so the UC-M6-1 check
  (shared channel, guests) trusts the `--channel-info` that the Claude Tag thread or the notify
  Routine reads with its Slack tool. bosun refuses when the facts are missing, malformed or for
  another channel, but it cannot prove them. The owner keeps the channel private, not shared and
  without guests; the M6 docs repeat this.
- **`--slack-user` is not verified.** bosun cannot verify `--slack-user`: the Claude Tag thread
  passes it from the Slack event, and any session holding the token could claim it. Thread spawn
  (S6) cannot verify `--slack-user` either; a thread spawn unlocks nothing a normal `bosun spawn`
  cannot: the same 7 checks and budget, no exemption from halt, process-red or main-red.
- **Later option: a Slack app.** If the owner wants bosun to verify the channel itself, a Slack
  app with a bot token (`SLACK_BOT_TOKEN`, env only, never printed; scopes `channels:read`,
  `groups:read`, `users:read`, and `chat:write` if bosun should post) can replace `--channel-info`
  with bosun's own `conversations.info` and member check. That is a spec change to §10 and an
  owner decision; M6 does not build it.
