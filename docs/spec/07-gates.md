## 7. Verification and the gate contract

Use cases: each "Done when" line of an item becomes `UC-<item>-<n>`. UC tests land passing in the
PR of the task that implements them; there are no pending UC tests (#179, option b). `bosun accept <epic>` checks that each UC test exists, is not pending,
and passes; only then does the epic close.

Gate contract (stack-agnostic):
- fmt, lint, types, deps, arch: on PR.
- test: on PR (affected packages) and in the merge queue (all).
- mutants, smoke, snapshots: in the merge queue.
- test-integrity: always, as a gate job.
- risk-check, review-verdict, main-open: always, each its own required check (D15); commit
  statuses today, check runs of the bosun App pinned in the ruleset after B2 (§15, D33);
  `bosun gate sources --pr N` checks which App posted each (read-only, §15).

CI templates call only `bosun gate <name>`. The channel's bosun.yml runs every gate in one job
`ci-ok` (or `bosun-ok`), which fails unless all succeeded: every job is billed as at least one
minute on a private repo (docs/ci-minutes.md). With a ts-pnpm stack (or mixed) it is two jobs
(§3): `bosun-trusted` runs test-integrity and deps with no PR code, and `ci-ok` (or `bosun-ok`)
runs install, fmt, lint and test only after it passed, so no PR code runs before or beside the
gates that must not trust it. bosun's own ci.yml runs them in one job `ci`, the same way (including the edit and draft-skip rules; every step that runs PR code, lint, test and the npm launcher tests, comes after the base's bosun, the pin check and the other gates), and `ci-ok` aggregates it. No PR code runs before the first gate that runs it (lint for rust; for ts-pnpm, the install in the second job): before anything runs rustc, cargo or a stack tool, both workflows put the base commit's `.bosun/` (the gate commands are in its profiles), every `.cargo` directory and every `rust-toolchain(.toml)`, every `.npmrc`, every `.pnpmfile.*` and every `deny.toml`, `.deny.toml`, `deny.exceptions.toml` and `.deny.exceptions.toml` (so cargo deny never reads the PR's policy) over the checkout and delete those the base lacks (a symlinked `.cargo` too), so a PR's edits to them never affect its own run and apply after merge (the run prints a notice naming them; a setup PR, whose base has no `.bosun`, keeps its own `.bosun` with a warning); bosun's ci.yml also pins `RUSTUP_TOOLCHAIN` to its rust-toolchain.toml channel (a test keeps them equal), the channel's toolchain step parses the base's toolchain file (python3 tomllib; only a `[toolchain]` with a plain `channel`, `components`, `targets` and `profile`) and exports `RUSTUP_TOOLCHAIN`, and both override cargo's rustc and wrappers with env (`RUSTC=rustc`, empty `RUSTC_WRAPPER` and `RUSTC_WORKSPACE_WRAPPER`). The gates stop at the first failure, so PR code never runs after a failure it could hide; the bosun binary's sha256 is checked before each gate as defence in depth. Residual: PR code in lint and test (and, for ts-pnpm, in the install and fmt of the second job) has the runner's sudo and can fake its own job's result, as in a gate job of its own before; the owner reviews R-ci. ts-pnpm residual: the PR's `pnpm-lock.yaml` is the audit's input, and its `packageManager` picks the pnpm release (an exact registry version) only while the base has none. Neither caches `~/.cargo/bin` (`cache-bin: false`): a cache a PR's earlier run saved must not put a binary on PATH (residual, as before: the restored `~/.cargo/registry` that the deps gate reads can come from such a run; not with two jobs, where bosun-trusted restores no cache). Jobs cache through
`keelstackhq/hoard@v0` (D19). A profile maps each gate to a command; the command runs without `GITHUB_TOKEN` and `GH_TOKEN` in its environment (it is repo code).

Profiles map gates to commands with the placeholders `{packages}`, `{files}` and `{diff}`. Each
profile has three adapters:
- packages: finds the affected packages from the diff;
- pending: finds and counts pending-test markers;
- assertions: counts assertions, so test-integrity can see a weakened test.

| Gate | rust | ts-pnpm |
| ---- | ---- | ------- |
| fmt | cargo fmt --check | prettier --check {files} |
| lint | cargo clippy --all-targets -- -D warnings | eslint --max-warnings 0 {files} |
| types | (in lint) | tsc -b |
| test | cargo test --locked -p {packages} | vitest run --project {packages} |
| deps | cargo deny check | bosun deps-check |
| mutants | cargo mutants --in-diff {diff} | stryker run --incremental |
| snapshots | cargo insta test --check | vitest snapshots |
| adapters | cargo-metadata, rust-ignore, rust | pnpm-workspace, vitest-fixme, ts-expect |

- bosun's own ci.yml adds a step that runs a pinned `tsc --strict` on the declarations `bosun schema --format ts` prints (test `ts_compiles_when_tsc_is_there`; `BOSUN_REQUIRE_TSC=1` makes a missing `tsc` a failure, and the step fails unless exactly that one test ran).
- Custom profiles and generic regex adapters are allowed; `bosun status` shows "reduced
  integrity" when a generic adapter is used.
- Generic adapters, for stacks bosun has no built-in adapters for (a repo profile `.bosun/profiles/<name>.toml`): `packages = "none"` (or `"generic"`) means the stack has no packages, so a per-package gate runs once over the whole stack with its `all` arguments; `pending = "regex"` and `assertions = "regex"` read `[adapters.regex]`: `test_files` (globs relative to the stack directory, required), `pending` (regexes; a matching line is a skip marker, and a `UC-…` id on it makes it a plan marker) and `assertions` (regexes; each match is one assertion). Both `pending` and `assertions` are `regex`, or neither, and each has at least one pattern. Profiles without `[adapters.regex]` are unchanged. There is no test counter, so `fewer-tests` does not fire for a regex stack. When any stack's profile uses a generic adapter, test-integrity still runs, and its data and `bosun status` say `"integrity": "reduced"` with `integrity_reason` (for example "stack py/ uses regex adapters", naming the stack path); otherwise `"integrity": "full"`. Adapter names are a closed set (packages: `cargo-metadata`, `pnpm-workspace`, `none`, `generic`; pending: `rust-ignore`, `ts-skip`, `regex`; assertions: `rust`, `ts`, `regex`): any other name is an error with a fix listing them, and `bosun status` shows such a stack as reduced. Every stack gets a kit, and the innermost stack holding a file decides which adapters read it.
- `bosun gate test` runs the built-in `cargo test ...` as `cargo nextest run ...` when `cargo nextest`
  is installed (CI runs nextest, one process per test, so a test that shares process state passes
  there and must pass here; it then also runs `cargo test --doc --locked ...`, which nextest skips, for the affected packages whose `cargo metadata` targets include a lib (`-p` each of them): a bin-only package gets no doc pass); without nextest, or with `BOSUN_NO_NEXTEST=1`, it stays `cargo test`.
- Rust test gate: the built-in profile's command is `cargo test --locked` (since 2026-11-10; was
  `cargo nextest run --locked`); the runner swaps in nextest when installed, as above, so doctests
  run through the extra `--doc` pass (only the built-in command is swapped, never a repo override). CI runs the release pinned in `.bosun/version`, and releases up to
  0.11.0 run nextest, so the channel's CI files keep installing cargo-nextest (prebuilt, seconds). `cargo test`
  also runs doctests, which nextest never ran: a repo with stale doctests may go red. A repo that
  wants nextest sets `[gates.test] cmd = ["cargo", "nextest", "run", "--locked"]` in
  `.bosun/profiles/rust.toml`; the channel CI files already install it.
- A mixed repo uses one `[[stack]]` per path (`path = "web/"`, `profile = "ts-pnpm"`).
- `unsupported = ["mutants"]` needs a reason and an owner approval (R-gov).
- Packages adapter (rust): a changed root `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml` or `.cargo/**`, or a changed `.rs`, `.toml` or `.lock` file in no package, means all packages; other files outside every package (docs) affect none.
- A profile may name its stack `manifest` (rust: `Cargo.toml`); a stack whose manifest is missing at the head and at the base skips each gate (exit 0, `skipped: true`, with a `reason`), so an empty repo after `bosun init` stays green.
- A gate may name `requires = "<file>"` (a path in the stack directory); the gate is skipped (`skipped: true`, `reason: "no <file>"`) only when that file is missing at the head and at the base, also with `--all`, like `manifest`: a branch that deletes the file still runs the gate.
- A gate may name `base_requires = "<file>"` (a path in the stack directory, a config file the tool judges against); the gate is skipped (exit 0, `skipped: true`, `reason: "no <file> in base: bootstrap PR, gate neutral"`) when that file is missing in the base commit, whatever the head has, also with `--all`. The PR that adds the config is thus not judged by the tool's defaults (cargo-deny without `deny.toml` rejects even MIT, while CI's `bosun-trusted` job runs with the base's config). Built in: rust `deps` has `base_requires = "deny.toml"`; ts-pnpm `deps` has none (`requires = "pnpm-lock.yaml"` already covers it: `pnpm audit` reads no other config).
- A profile may name a `lockfile` (rust: `Cargo.lock`, a path in the stack directory). When a gate whose `cmd` contains `--locked` (rust lint and test) fails and the stack has no such file at the head, bosun returns one error (exit 1) naming the file, with `error.fix` "run `cargo generate-lockfile` and commit Cargo.lock", in place of cargo's raw failure (which still goes to stderr); the failed run is in `data`. With the file present the failure is the plain `gate <name> failed (exit N)`.
- In a gate's `cmd`, an item that is exactly `{packages}` marks where the `each_package` (or `all`) arguments go, for tools whose filters must come first; without it they are appended. The profile's `packages` adapter (see the closed set above) loads the packages and says which a diff affects; an unknown adapter name is an error with a fix.
- ts-pnpm profile: the gates call the workspace's root `package.json` scripts, so a repo chooses its tools: fmt runs `pnpm run format:check`, lint `pnpm run lint`, types `pnpm run typecheck`; test runs `pnpm --filter ...<pkg> run test` for each affected package (`...pkg` selects the package and its dependents, so `data.packages` lists the changed packages and the run covers their dependents too) and `pnpm -r --include-workspace-root run test` for all; deps runs `pnpm audit --prod --audit-level high` and `requires` `pnpm-lock.yaml`. With `--include-workspace-root` the gate runs the root project's own `test` script too, so the root `test` script must not be a recursive `pnpm -r run test` (it would run every package twice). Packages adapter `pnpm-workspace` reads the `packages:` globs of `pnpm-workspace.yaml` (a block list or a one-line list `[a, 'b']`; any other value, or a glob with braces, is an error with a fix) and the directories with a `package.json` that has a `name`. It does not enter dot directories, symlinks or `node_modules`; it skips directories named `target`, `dist`, `build` or `coverage` unless a `packages:` glob matches that directory (`packages/build` is a package when `packages/*` is listed). A changed file inside a package affects that package, whatever its extension. A root `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `.npmrc` or `.nvmrc`, or a file with extension ts, tsx, mts, cts, js, jsx, mjs, cjs, json, yaml or yml in no package, means all packages; other files outside every package (docs) affect none.
- The changed files that select a gate are the commits against the base plus the working tree: staged, unstaged and untracked files count too, so a gate run before the first commit is not skipped. `data.uncommitted` lists those uncommitted paths under a stack; in CI it lists only the base-config files the workflow restores into the working tree, and those may appear there when the base changed them since the merge base. A git failure while listing is noted on stderr and counts as none. `test-integrity` judges four views, the commits (merge base to HEAD), the index (merge base to what is staged), the working tree (merge base to the files on disk) and the untracked, non-ignored files (`ls-files --others --exclude-standard`) as added files read from disk, and refuses if any has a finding (the same finding is reported once), so restoring a file in a later view cannot hide a weakening in an earlier one; it reads paths NUL-separated (`-z`), so unusual names are not skipped; an error listing any view fails the gate (exit 1). The `{diff}` file (mutants) is the merge base against the files on disk, plus every untracked file as a new file, because `cargo mutants --in-diff` reads it against the working tree.
- On CircleCI (env `CIRCLECI=true`), `bosun gate` and `test-integrity` find their base from `CIRCLE_BRANCH` and the default branch (from `origin/HEAD`, else `main`). `CIRCLE_BRANCH` is author-controlled, so a pipeline with `CIRCLE_PULL_REQUEST` or `CIRCLE_PR_NUMBER` set is a pull request whatever its branch is called. A merge-queue branch (`gh-readonly-queue/<base>/pr-<n>-<sha>`) is trusted only when `<base>` is the default branch and `<sha>` is an ancestor of `origin/<default>` (`git merge-base --is-ancestor`); otherwise bosun prints one line on stderr and treats it as a pull request. A trusted queue branch only sets the event and runs every gate (`all`); its sha never sets the diff base, because an older ancestor would hide what main gained since. With `--base` the queue check is skipped; a push to the default branch runs every gate against `origin/<default>`; a pipeline with no branch (tag build, API or manual pipeline; event `unknown`) runs every gate; every other CircleCI run (a pull request, an untrusted or trusted queue branch, any other branch) diffs against `git merge-base HEAD origin/<default>`. `--base` sets the diff base and `--all` forces every gate; the default-branch, merge-queue and unknown pipelines run every gate regardless. The gate output then carries `data.ci` `{provider: "circleci", event: "pr"|"push"|"merge-queue"|"unknown", base}`; GitHub and local runs keep the rules above and carry no `ci` block. A CircleCI checkout without `origin/HEAD` in a repo whose default branch is not `main` looks for `origin/main`, fails closed (exit 1, with the fetch fix) and never skips; so does a pull request whose `git merge-base HEAD origin/<default>` fails.
- A gate with `each_package` and `when_no_package = "skip"` is skipped (exit 0, `skipped: true`) when no package is affected; the default `when_no_package` is `run`, which runs the gate with its `all` arguments.

Time budgets: a PR run is at most 10 min, a merge queue run at most 15 min, one gate at most 8 min.
A gate over budget opens a lesson.

Drafts skip CI (docs/ci-minutes.md). A PR that is not finished is a draft, and `bosun pr` opens
it as one. Every heavy job (the work, gate and trusted jobs) of a workflow that a `pull_request` or
`pull_request_target` event starts has the job-level
`if: github.event_name != 'pull_request' || github.event.pull_request.draft == false` (a push,
merge-group, schedule or comment event still runs), so a draft starts no runner there. The
required aggregate `ci-ok` / `bosun-ok` is never skipped, because a skipped required check counts
as passed (a stale green): it keeps `always()`, runs on a draft and its first step fails with
`draft: CI not run, mark ready for review` (in the channel's rust single-job variant, where
`ci-ok` is the work job, the plan step fails first, before any heavy step). `ready_for_review`
(listed in every such trigger's `types`) runs everything. `risk` and `main-open` skip drafts
(they post a status; none is posted until the PR is ready). The CircleCI pipeline has no draft
flag and still runs on drafts (S12, open).

`bosun gate ci-minutes` (built in, like test-integrity: it is not in a profile, runs no repo code
and needs no GitHub) reads `.github/workflows/*.yml` and `*.yaml` with a small line-based reader
(no YAML crate; it understands the subset these workflows use and is conservative) and fails
(exit 1, `data.findings` = `{file, job, rule, fix}`, `error.fix` the first fix) on:
- `draft`: a `pull_request(_target)` workflow with a job whose job-level `if:` lacks
  `pull_request.draft == false` (or `!= true`, or `!github.event.pull_request.draft`) as a term of a conjunction
  (`always() || ...draft == false` never skips; under `pull_request_target` only the plain test
  counts, the event-name form never skips; an `||` branch `github.event.label.name == '<label>'`
  may judge a draft, as main-open does for the mainfix label); the aggregate jobs `ci-ok` and
  `bosun-ok` and a fail-fast job of any name (its first step reads `pull_request.draft` and exits
  non-zero) are exempt;
  a job confined to other events (`github.event_name == 'push'`), a job that `needs:` a
  draft-skipping job (no status function in its `if:`) and a `pull_request` trigger whose `types:`
  has none of opened, synchronize, reopened, ready_for_review, edited need no guard (quoted `if:`
  values and `<<:` merge keys are read);
- `aggregate`: `ci-ok` or `bosun-ok` whose `if:` skips drafts (it must run and fail on a draft), or
  that has `needs:` and an `if:` without `always()` (a skipped need skips it), or that has `needs:`
  and no step failing on a draft (a step that reads `pull_request.draft` and exits non-zero, or a
  `test` that a `needs.*.result` is `success`);
- `ready_for_review`: such a trigger whose `types:` lacks `ready_for_review` (no `types:` is the
  default set, which lacks it);
- `concurrency`: a `pull_request`, `pull_request_target` or `push` workflow without a top-level
  `concurrency:` whose `cancel-in-progress` is not `false` (an expression counts);
- `paths`: a heavy job (a `macos*` or `windows*` runner, or a matrix) on a `pull_request(_target)`
  trigger without `paths` or `paths-ignore`.
Workflows started only by `schedule`, `workflow_dispatch`, `workflow_run`, `issue_comment`,
`workflow_call` or `status` are exempt. A comment `# ci-minutes: allow <concurrency|paths> <reason>`
switches off one of the last two rules for a file (bosun's release.yml never cancels a release).
`bosun doctor` reports the same findings as step 14 "CI minutes" (missing if any; ok without
workflows). bosun's own ci.yml, the channel's bosun.yml and the local loop in AGENTS.md run it right after
test-integrity (it runs no repo code; ts-pnpm keeps it in `bosun-trusted`). The channel skips it
with a notice when the pinned bosun is older than 0.7.0, which has no such gate; bosun's ci.yml also runs `gate ci-minutes --all` with the release a PR pins when the PR moves `.bosun/version` (main runs the gates with it right after the merge, so a newer gate cannot turn main red);
`tests/cli_gate_ci_minutes.rs` and `tests/channel_render.rs` also run the check on bosun's own and
on every rendered workflow. Later: a per-PR minutes report (jobs started and billed
minutes per push, from the Actions API) as a `bosun` command or a comment; not built.

test-integrity:
- Refuses a PR that deletes a test, adds a skip marker, or lowers the assertion count, unless the
  plan says so.
- A snapshot change needs the line `snapshot-change: <reason>` in the PR body.
- The PR body and the allowed kinds (`delete-test`, `skip`, `only`, `fewer-asserts`) come from env `BOSUN_PR_BODY` and `BOSUN_INTEGRITY_ALLOW` (comma-separated) for `bosun gate test-integrity` and `bosun test-integrity`. With `--pr <n>`, `bosun test-integrity` reads them from GitHub instead: the PR's body, and the `allow` list (unknown kinds dropped) of the first issue the body links (`Closes #N`, `<!-- bosun:task-pr N -->`, in body order) that has task metadata and whose `touch` covers every path the PR changes: added files and both names of a rename too, only the fragments pass (`core::touch::outside` with every path checked as an edit; stricter than `bosun pr`, so an add-only PR cannot borrow `skip` or `only`). The PR body is the agent's, so it chooses which task to link; the touch rule closes that: a task lends its list only to its own work, as the plan PR approved both its `touch` and its `allow`. No covering task, or a cut file list (fewer files listed than `changed_files`, or 3000), allows nothing. `data.task` (or null) and `data.allow` say what was used, and `data.allow_refused` why nothing was. The plan task's `allow:` key (docs/plan-format.md) puts the list in the task metadata at import. Residual risk: the task issue body is editable by anyone with write access, agents included, like the task's `capabilities`; an allowed finding is still listed in `data.findings` with `allowed: true`. Follow-up, not built: once auto-merge is turned on at PR open (#335), the task's task-pr record exists when CI runs, and `--pr` can also require that the task's newest task-pr record names this PR. The error's fix names the cure: a `snapshot-change: <reason>` line in the PR body for a snapshot change, else restoring the test or the plan task's `allow:`. Findings the task allows are reported with `allowed: true` and do not fail. A `#[ignore = "UC-…"]` marker that the base file lacks (by id) is a new skip; removing one is fine. A lower count of `#[test]`, `#[tokio::test]` and `#[rstest]` attributes in a file is a `fewer-tests` finding, allowed by `delete-test`. Files are compared with the merge base, not the base tip. Template tests (crates/common, its test) are removable in the bootstrap PR. Bootstrap: when the merge base has no `.bosun/` directory (the base is the bare template render, so this PR adds bosun), `deleted-test` and `fewer-tests` findings are allowed (`allowed: true`, `reason: "bootstrap: base has no .bosun"`), so tests the template shipped can be removed; `new-skip`, `new-only`, `fewer-asserts` and `snapshot-change` are refused as ever. Later, a file `.bosun/template-tests` in the merge base lists glob paths (one per line, `#` comments, touch-glob syntax) of template-shipped tests whose `deleted-test` and `fewer-tests` are allowed the same way (`reason: "template-tests: listed in base .bosun/template-tests"`). It is read from the base only, never from head, so a PR cannot allow its own deletions. Findings carry `reason` only when allowed this way. Template sources are not tests of the repo: a path under `template*/pieces/*/files/**` or `channel/pieces/*/files/**` (render input of a template or channel repo, such as hull or bosun's channel) is never a test file, so moving it to `.jinja` or dropping a test there is no finding; the rendered repo's own test-integrity checks the tests.
- ts adapters: test-integrity reads `.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs` and `.cjs` files with them, `.rs` files with the rust adapters, and no other file is a test file. Test files are `*.test.<ext>`, `*.spec.<ext>` and files under `__tests__/`. Comments (`//`, `/* */`), regex literals and the inside of string and template literals are ignored; `fit` and `fdescribe` count only when called with a string or template literal title, and a name after `function` or `.` is not a declaration. `ts-skip` finds `it`, `test` and `describe` (also `suite`) declarations with a `.skip`, `.todo`, `.skipIf`, `.runIf` or `.fixme` modifier anywhere in the chain (`describe.skip.each`, `test.concurrent.skip`), and `xit`, `xtest` and `xdescribe`; a new one is a `new-skip` finding. A new `.only` (`it.only`, `test.only`, `describe.only`, `fit`, `fdescribe`) is a `new-only` finding, allowed by `only`. `ts` counts `expect(`, `assert(` and `assert.`, and `it`/`test` declarations (skipped ones too) for `fewer-tests`. Each side of a change is read with the adapter for its own path; a file that was a test file and no longer is one (renamed to `a.test.ts.disabled`) is a `deleted-test` finding.
- Mutants that survive fail the merge queue.
- In GitHub CI (`ci.yml` here, `bosun.yml` in the channel), a step `task allow list` runs before the gates on a pull request: it runs the checked base (or pinned) bosun as `bosun test-integrity --pr <n>` with the run's read-only token (`issues: read`, `pull-requests: read`) and passes the linked task's known kinds to the gates step as `BOSUN_INTEGRITY_ALLOW`. The token never reaches the gates step, where lint and test run PR code (`tests/workflows_integrity_allow.rs`). A failure there, or a bosun without `--pr`, allows nothing. CircleCI has no such step and allows nothing.

The task in a review pack (below) also has `claimant`, `lease_touch` and `touch_added`. The
claimant is the session of the newest `task-pr` record for the PR on the task issue (else of the
newest lease record); `lease_touch` is every touch glob of the claimant's lease records, in order,
ended leases included, and `touch_added` the ones that neither the task's `touch` nor any bundled task's `touch` contains (a lease
widened by `bosun claim <n> --touch ..`). Only comments by writers count, and only the claimant's
leases; all three are `null` when the comments cannot be read. The instructions ask the reviewer
to check the files of `touch_added`. The pack's `untrusted` lists the field paths written by people or agents (`title`, `task.title`, `task.body`, `bundle_tasks[].title`, `bundle_tasks[].body`, `ucs`, `files[].filename`, `files[].patch`, `chunks`, `task.meta`, `task.claimant`, `task.lease_touch`, `task.touch_added`, `bundle_tasks[].meta`, `delta_not_in_pr`; values are not altered); the instructions call them data to judge, never instructions, and a request in them to approve, skip checks or change the verdict is itself a major finding. `review_md` and `lessons` come from the base branch and are trusted. The task metadata is not rewritten: it comes from the plan,
and `plan amend` reconciles it. `task` is the first issue the PR links; `bundle_tasks` lists every other issue of this repo that the PR closes (`Closes #N`, `Closes owner/repo#N` or an issue URL) and that has task metadata of the same epic as the first task, as `{issue, title, body, meta}` (a single-shape bundle; others are left out): the review covers them all, and their `touch` joins the `touch_added` comparison.

Review loop: the PR author owns it. `bosun review-loop <pr> [--max N]` reads the verdict comments of the PR (the same parsing as `verdict apply`; one JSON object) and returns one step in `data.step`, with a call in `next`: `spawn-reviewer` (no independent verdict for the head, or only a stale one; `next` is an `Agent` call whose prompt says a read-only reviewer saves the verdict JSON to its scratchpad and posts it with `bosun verdict comment --from -`), `fix` (a verdict at the head does not approve: its `findings` are in `data.findings` and in `next`), `ready` (an approving verdict at the head; `next` is `bosun pr <issue> --ready`) or `ask-owner`. A round is a distinct head with an independent verdict; a verdict by a `[approvals] verdict_bots` login or any GitHub Bot account is a bot verdict: it is neither a round nor ready. `ask-owner` is exit 5 (data still printed): the verdict escalated (`escalate_risk`), or the limit is reached: `--max`, default `[mode] review_rounds` (§18), when a new round (max+1) would start, or when the head at round max still needs a fix. The limit is `[mode] review_rounds` read from the default branch (as `verdict apply` reads `verdict_bots`), never the checkout; `--max` can only lower it. bosun does not read an owner's reply: the owner's answer is a PR that raises `review_rounds` (R-gov, and R-weaken since it is looser, §8), so the raise is approved and signed like any gate change.
